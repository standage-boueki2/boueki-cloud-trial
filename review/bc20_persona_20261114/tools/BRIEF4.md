# 4回目の評価（最終版の確認採点）— 全担当共通

3回目（`findings3/`）で全員 4点でした。残った課題に 6本の直し（r3a・r3b・r3c・r4a・r4b・r4c）を入れた最終版ができています。
4回目は、**最終版** を同じペルソナで操作し、(1) 3回目に残った課題が直ったかを1件ずつ確かめ、(2) 総合点と画面ごとの点を付け直します。目標は「どの人も 5点」。届かない所は、再現できる事実で残します。

## 見る版
- 最終版：**`BASE=http://127.0.0.1:8815/`**（`lib.cjs` は環境変数 BASE を見る。必ず付ける）
- 3回目のときの版：`http://127.0.0.1:8814/`
- 道具：`scratchpad/tools/README.md`、ペルソナの定義 `scratchpad/tools/BRIEF.md`、3回目の決まり `scratchpad/tools/BRIEF3.md`（進め方の 3・4 は今回も同じ）

## 進め方
1. 自分の3回目の結果 `scratchpad/findings3/<ID>.json` を読む（ペルソナ・点数・`to_5`・`issues`＝M の課題・`recheck` で partial／open だったもの）。ペルソナは同じ人。
2. **3回目の課題（`<ID>-M..`）と、partial／open だった前の課題を、同じ手順で 8815 で確かめ直す**：`fixed`／`partial`／`open`／`worse` と、見た事実（画面の文言）を1行。各ペルソナの `to_5` に書いた項目は必ず全部確かめる。
3. P2・P3 の主な流れ（バイヤーを足す → 商談を記録 → 案件 →「書類をつくる」→ 建値を変える → タスク・受信箱・分析の数字）、P1 の「資料の登録から『次は』だけで最後まで」を、通しでもう一度行う。直しで別の所が壊れていないか（前はできた操作ができない・数字が合わない・表示が崩れた）も見る。
4. 点は事実で付ける。**甘くも辛くもしない**。
   - 5＝その人の目的が迷わず達成でき、誤り・表示崩れ・数字の食い違いが、その人の使う範囲に無い。
   - 4＝目的は達成できるが、その人が実際に引っかかる課題（minor 以上）が残っている。polish（言い回し・数px）だけなら 5 を付けてよい。
   - この環境だけの事情（AI 未接続・同期サーバーが代役・外への通信が止められている・「開発中」と明記された画面）は減点しない。**アプリが持っていないデータ**（ひな形の無い品目の関税率・カテゴリー別のバイヤー数 など）は、「要確認」と調べ方の入口が明示され、行き止まりにならなければ減点しない。別ファイルのガイド（`guide/`）の中身も、アプリ側に案内があれば減点しない。
5. 新しく見つけた課題は `<ID>-Q01` から。証拠（画面の文言の引用か画像の絶対パス）のない課題は載せない。

## 提出物
`scratchpad/findings4/<ID>.json`（形は3回目と同じ。`base` は "8815"、ペルソナは `overall_r3` と `overall`、`to_5`）。人が読む要約は `scratchpad/findings4/<ID>.txt`。

## 守ること
- 事実だけ。作業は `scratchpad/agents4/<ID>/` の中だけ。`tools/`・`build/`・`fix/`・リポジトリ・サーバーには触らない。git の操作はしない。
- 機械が混んでいる。ブラウザは同時に1つ・1回 90秒以内。画像は要所だけ（全部で 20 枚まで）。
- スクリプトは Write の道具で書く（Bash のヒアドキュメントで JS を書くと止められる）。出力は `cut -c1-300` で短く。`curl` は `-o /dev/null`。
- 途中で止まっても残るよう、ペルソナ1人が終わるごとに json を書き出す。
- 最後の返事は短く：ペルソナ別の総合点（3回目→今回）、3回目の課題の結果の数（fixed／partial／open／worse）、残っている課題を重い順に全部（番号・画面・一行・誰が引っかかるか）、提出ファイルのパス。
