■ 原因（計測で分かったこと）
  A. 読み込み中に画面が何度も別の形で描かれる（＝カクカクの正体。8820 からある。8811 で回数・時間が増えた）
     ・刷新版の層（21.93 の 50本＋この作業の 58本＝script 56・link 52）は本体の 16MB のあとに1本ずつ読まれ、そのたびに解析が止まって描画が挟まる。
       読み込みの途中の絵（CPU 1/4・8811・food の画面の絵）：0.8s 白 → 5.0s 本体の前のデザインのダッシュボード → 9.4s 途中まで仕上げた画面 →
       10.5〜13s「こんばんは！」の前のホーム → 21.4s やっと案件一覧（log/sheet_8811_x4.png）。
     ・layout shift の合計（CLS）：8820 0.90〜1.43・8811 0.90〜1.11（本体だけの 8803 は 0.003〜0.063）。
     ・rd.js は読まれた直後から 0.5 秒おきの見張り（40 回＝20 秒）で RDX.after を回し、その時点で読まれている層だけで画面を仕上げる。
       r5b はその対策に「最後の層で render() をもう1回」を足していた（rd_v92z90r5b.js の評価だけで 113ms）。
  B. 読み込みのあとも 20〜30 秒、画面のどこかが描き直され続ける（主に 8811 で増えた分）
     ・rd.js の 0.5 秒おきの見張りが、何も変わっていなくても RDX.after を最後まで回す。RDX.after はこの作業で 34 層に包まれ、
       1 回 約40ms（CPU 1/4 で約150ms）。8811・food：15秒で 23〜25 回・約1.0〜1.1秒（8820 は同じ回数で 270ms）。CPU 1/4 では 34〜41 回・6.0〜6.4 秒。
       その度に左のメニュー（#rdside）を作り直し（15秒で 31 回）、用語集の箱が消えては足され（27 回＝出たり消えたり）、上の帯の会社の札を作り直す（66 回）。
     ・RDX.after の中の「表示されているか」の確かめ（rd_bar.js の shown＝getComputedStyle、rd_case.js の shortBtns＝getClientRects、
       rd_v92entry.js の shown）が、直前の書き込みのせいで毎回スタイル・配置の計算をさせる（8811 x1・15秒：shown 396ms・shortBtns 392ms・entry 147ms）。
       スタイルの再計算：8820 343 回・432ms → 8811 576 回・1,836ms（CPU 1/4 では 477 回 2.1s → 769 回 10.8s）。
     ・rd_case.js の shortBtns（21.93 の層。1.5 秒おき＋RDX.after のたび）は、縮めなかったボタンに空の印（data-kfull=""）を付けるが、
       「印がある（空でない）なら飛ばす」形のため、毎回やり直す（約100か所の getClientRects と属性の書き直し。DOM の変化の知らせが 1 秒に約100件・ずっと）。
  C. 読み込みのあともずっと回る処理（8820・8803 も同じ。21.84 の層）
     ・v84k（保存の鍵の封）：v84kSeal の中の v84kMarker がセッション（sessionStorage bc20_ses_v1）を同じ中身で書き直す →
       v84kSesPut が v84kSealSoon（30ms 後にまた封）を呼ぶ → … の繰り返し。15 秒で 400 回の書き込み（399 回は同じ値）・暗号化と IndexedDB の書き込み。
       読み込み後 4〜15 秒の CPU 908ms のうち 約500ms がこれ（CPU 1/4 では約2秒）。
  D. 文書の解析が終わる（DOMContentLoaded）まで：8803 1.3s／8820 2.6〜3.3s／8811 3.2〜3.6s（x1）。刷新版の層の 108 本を1本ずつ
     取り寄せ→解析→実行（その間にタイマー・見張りが挟まる）で 2 秒あまり。取り寄せそのものは合計 0.6 秒（1本 6ms）で、待ちと間の処理が大半。
  E. そのほか（本体。8803 にもある・残した）：入るときの render が 3 回（authBoot の途中＝後ろの層がまだ無い状態で1回／21.7 の setTimeout(0) でもう1回／
     同期サーバーへのログインと取得のあと syncReloadState でもう1回）。1回 約250ms（CPU 1/4 で約1秒）。描き直しのたびに、上の帯の高さを読む ux17SecTop・
     スタイルの並べ替え（ux25CssLast ほか 5 本が互いに「いちばん後ろ」を取り合う）・v39 のサニタイザ（足された要素を全部なめる）が走る。

■ 残したもの（理由）
  1. 本体の重さ（8803 にもある）：入るときの render が 3 回（authBoot の途中＝後ろの層がまだ無い状態／21.7 の setTimeout(0)／同期の取得のあとの syncReloadState）。
     1回 約250ms（x4 で約1秒）。3回目（syncReloadState）は「取得で何も変わっていなければ飛ばす」を試したが、毎回、成長レベル・画面の位置（navl）・
     ゴミ箱の印（tomb）・アカウントの台帳の使用状況が書き換わり、同期の層（18.5・56・43 ほか）が取り込みの後始末もしているため、
     「変わっていない」を安全に決められず、入れなかった。画面が出たあと x1 で約0.3秒・x4 で約1秒、1回固まる。
  2. 本体の 16MB の解析と実行（x1 0.5秒・x4 2秒）と、描き直しのたびに走る ux17SecTop（上の帯の高さを読む）・スタイルの並べ替え（ux25CssLast ほか 5本が
     互いに「いちばん後ろ」を取り合い、render 1回で <style> を何十回も動かす）・v39 のサニタイザ。本体の作り（コードの分け方）を変えないと減らせない。
  3. 読み込みのあとも残る小さな定期の書き換え：rd_bar の build（1.5秒おき・会社の札を innerHTML で作り直す）、r4c の「すべての機能」の札の属性、
     rd_v89badge の札、rd_v92entry（0.9秒おき）など。1秒に約13〜26件（8803 は 0〜12件）。見た目は変わらない。
  4. v84 の「更新」は、1回目の文書を window.stop() で止めて読み直す（21.84 の作り）。x1 で 40〜120ms、x4 で 200〜500ms。
  5. Service Worker（sw.js）は、取り寄せたものを毎回 Cache Storage に入れ直す（16MB の index.html も）。この環境の Playwright では SW が画面を受け持たず、測れていない。
     まとめたことで、入れ直す数は 110 → 5 になる。
  6. r8b の html.k-r8b-glside（見出しの下の説明を隠す）は、8811 の見た目に合わせて CSS で打ち消した（直し 6.）。隠すかどうかは決めが要る（r8x の 9. と同じ）。
  7. 6/6 まで進んだアカウントの保存は IndexedDB（暗号の鍵つき）にあり、別の origin に写せない。c66b（3/6・国と規制まで）で代えた。
  8. 注意（ほかの担当の層へ）：読み込みの間（DOMContentLoaded まで）は RDX.after が動かない（最後に1回）。層を読み込んだ時点で RDX.after を呼んで、
     その結果（見出しなど）を当てにする書き方はしない（RDX.after を包んで、その中で直せば今までどおり効く）。
     build.py は rd_v92*.js／.css を全部 rd_v92all.js／.css にまとめる（新しい層もそのまま入る。いちばん外に宣言を書くと、まとめた 1 本の中で名前がぶつかるので、
     今までどおり (function(){ … })() の形で書く。構文の通らないファイルは自動でまとめずに別のタグにする）。名前に boot が入る rd_v92*boot.* は特別な場所に置かれる。
